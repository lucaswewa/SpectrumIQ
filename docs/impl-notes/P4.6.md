# P4.6 — OME-TIFF export — implementation notes

- **Status:** Review
- **Branch / commits:** `phase/P4.6-ometiff`, from `main` at `e94680b`
- **Date:** 2026-10-25

## Summary

- **The `tiff` crate's encoder, evaluated:**
  - it does BigTIFF;
  - its image encoder writes strips only, with no tiles and no SubIFDs;
  - its low-level `DirectoryEncoder` writes raw data, any tag, unchained directories and `IFD8`
    arrays.

  So the export writes its tiles and tags through `DirectoryEncoder`, and the crate does the
  file's structure. No writer of our own (ADR-0046).
- **`siq_storage::ometiff`** (ADR-0046):
  - **`export`:**
    - an OME-Zarr image as one BigTIFF;
    - an IFD per plane in `XYZCT` order, with level 0;
    - levels 1 and up as each plane's SubIFDs (`NewSubfileType` 1, listed as `IFD8`);
    - tiles of 512, padded with zeros, deflated or not compressed;
    - IFDs and their values on word boundaries.

    Tiles are read from the levels and encoded in parallel on the calling pool, in batches of 64,
    and written in order. The file is written as `<out>.part`, renamed once whole, and removed if
    the export is cancelled or fails.
  - **`ome_xml`:** the 2016-06 OME-XML, in the first IFD's `ImageDescription`, in UTF-8.
    - The image: `XYZCT`, its type, sizes and µm pixel size.
    - The channels, with their colours.
    - A `TiffData` and a `Plane` (with its position) per plane.
    - From the manifest: the acquisition date, a description, and a `MapAnnotation` of the
      dataset's provenance.
  - **`estimate`:** the memory held, (64 + 3 × threads) tiles.
- **`siq_storage::Control`:** the progress and cancellation trait, moved from `siq-pyramid`, which
  re-exports it, so the export and the builder share it. `StorageError` gains `Tiff` and
  `Cancelled`.
- **`siq_jobs::kinds::OmeTiffExportJob`** (`export_ome_tiff`):
  - takes the manifest from the job's dataset;
  - reports progress by tiles, and honours cancellation;
  - records the file as its output.

  The three jobs now share one helper for their output's path in the dataset.

- **Public:**

## Deviations

1. **The OME-XML is UTF-8, not ASCII with character references.**
   - The first version wrote `&#181;m` (and any non-ASCII name) as references, to keep TIFF's
     text 7-bit.
   - Fiji's Bio-Formats then read the file as plain TIFF. Its XML sanitiser turns every `&#` into
     ` #`, so the units failed to parse (`' #181;m' not a supported value of UnitsLength`).
   - The `tiff` crate's text value refuses non-ASCII, so the description is written as raw bytes
     typed `ASCII`, as Bio-Formats' own writer does.

### Manual checks

Each was run on `export_ometiff`'s file (12 000 × 8000, two channels, rings and a grid, seven
levels). This PC's service session has no display, so the GUI tools ran headless, through scripts
kept outside the repository.

- **Fiji,** the stable build (March 2026, Bio-Formats 8.1.1) and the latest (23 October 2026,
  Bio-Formats 8.5.0), alike:
  - **Bio-Formats picks `OMETiffReader`:** format OME-TIFF.
    - One series, seven resolutions from 12 000 × 8000 to 188 × 125, tiles of 512.
    - `uint16`, `XYZCT`, two channels named `rings` and `grid`, green and magenta.
    - 0.376 µm, the acquisition date, the description, and the map annotation.
  - **Pixels:** 16000, 12000 and 500 where the pattern puts them, at resolution 0; and the
    expected values at resolution 3.
  - **The importer's code path** (`BF.openImagePlus`, as File › Open runs it) opens a 16-bit
    composite image: 12 000 × 8000, two channels, 0.376 micron, green and magenta LUTs, the same
    pixels. Its series 4 is resolution 3, at 1500 × 1000.
    - Opened alone, a reduced resolution has default LUTs and no pixel size: Bio-Formats gives
      sub-resolutions no OME metadata.
    - The importer's own dialog can't be built headless in either build (a `VerifyError` in
      `MainDialog`, whatever the file). Opening it in Fiji's window is left to a desktop session.
- **QuPath 0.7.0,** in its console mode (`QuPath script -i`):
  - a `BioFormatsImageServer`: 12 000 × 8000, two channels, `UINT16`;
  - seven resolutions, downsamples 1 to 64;
  - 0.376 µm;
  - channels `rings` (`#ff00ff00`) and `grid` (`#ffff00ff`);
  - the right pixels, and the whole image read at downsample 8 as 1500 × 1000.
- **tifffile 2026.9.20:**
  - BigTIFF and OME;
  - series `CYX` (2, 8000, 12000) with seven levels, each equal to the OME-Zarr's;
  - tiles 512 × 512, `ADOBE_DEFLATE`.

  ome-types validates the OME-XML against the 2016-06 schema.
- **The OME-Zarr in Fiji** (ADR-0042's follow-up, now its amendment):
  - the stable build (`n5-zarr` 1.5.1) knows Zarr v2 only, and finds no container;
  - the latest (`n5-zarr` 2.0.1) reads it through `ZarrV3KeyValueReader`. It discovers the
    OME-NGFF metadata with seven scales, and opens level 0 as a 16-bit ImagePlus with the right
    pixels.
